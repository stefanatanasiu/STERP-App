# BOM - intentional technical debt

Legacy texture deliberately kept in the bills of material module, with the modernisation hint for
each item. Nothing here is an accident; it is the kind of thing a 1990s manufacturing system grew.

| File / pattern | What it is | Why it is like that | Modernisation hint |
|---|---|---|---|
| `BOMEXPL.cob` - recursion through a flat occurrence pool (`BOMWORK`, `BOMOCCUR`) with a `BX-NODE-*` state block passed back into the program | the explosion keeps its own stack in working storage instead of using a real tree structure | COBOL 85 had no dynamic allocation; the pool was sized for "the biggest bill engineering could imagine" (5,000 occurrences) | a recursive service over a typed tree; let the database do the recursive CTE for structure-only views |
| Fixed table limits: 25 lines per paging window, 10 option groups, 10 splits, 30 supply rows | every COMMAREA is a fixed-size record | CICS COMMAREAs were capped and the screen showed 25 lines | paged REST responses with a continuation token |
| The result "stays in the pool until the next EXPLODE" | paging reads the previous calculation, it does not re-explode | re-exploding a 2,000 line bill for every page of 25 was unaffordable | stateless query with a cached result id |
| `BOMMATH` reimplements rounding instead of calling a shared numeric service | rounding is at the declared production/supply boundary with the unrounded value retained alongside | the shared `RNDALLOC` rounds allocations, not production quantums | one rounding policy service with the boundary as a parameter |
| Reason codes `BOM0501..BOM0535`, `BOM0701..BOM0715`, `BOM1101..BOM1107`, `BOM1401..BOM1445`, `BOM1500..BOM1507` hard-coded in each program | message text and code live in the program that raises them | there was no message catalogue in 1996 | message catalogue keyed by reason code, translatable |
| `ECOIMPCT` builds `bom.BomChangeImpact` rows with literal SQL `INSERT ... SELECT` strings assembled by `STRING` | dynamic SQL built in COBOL working storage | the pre-compiler licence only covered static SQL on the mainframe, so the PC port used SQLIO | parameterised repository / ORM; the statements are already parameterised, only the assembly is manual |
| Kit and demand impact rows are *posted into* `bom.BomChangeImpact` by other modules rather than read from them | the table is the hand-over point between BOM, Kits and Order Entry | each module owned its own files; cross-module reads were forbidden by the 1998 architecture rule | domain events, or a read model that queries the owning services |
| `bom.tr_BomReleasedImmutable` treats an identical rewrite as "not a change" | the trigger compares the engineering columns instead of blocking every UPDATE | the nightly structure re-load rewrites every row; blocking it outright would have stopped the batch | immutable append-only revisions; no UPDATE path at all |
| Release validation compares a SHA-256 "content hash" computed in two places (`BOMVALID` and `bom.usp_ReleaseBom`) | the same concatenation rule is coded in COBOL and in T-SQL | the release gate had to work from the green screen and from the batch run | one hashing service called by both |
| `BOMRP010` prints both an indented and a costed layout from one program selected by `MODE=` | one report program, two `DETAIL` records | each new report needed a change request; adding a mode was cheaper than a new program | report definitions with a shared data source and separate layouts |
| `BOMRP030` does the same for two *different reports*: `core.ReportDef` rows `BOMRP030` (where used) and `BOMRP040` (revision comparison) both point at the one `BOMRP030.exe` and are told apart by `MODE=` | one program, two `DETAIL` records, two report ids, one spool name pattern | the 1999 report catalogue charged per program name, so a second "report" was added as a mode of the first | one report definition per output, sharing a query service |
| `BOMRP030` builds its column captions, section banners and footers as 132-byte `X(66)+X(66)` strings filled by reference modification (`MOVE "Rev" TO Ws-Caption(39:3)`) | the heading text is positioned by hand, column by column | Report Writer cannot choose between two `CONTROL HEADING` layouts at run time, and the column positions had to follow `MODE=` | a layout description (column, width, caption) driven from data |
| `BOMRP030` prints the subject block as a `DETAIL` group it generates once, not as a `CONTROL HEADING FINAL` | an ordinary detail doing a heading's job | this GnuCOBOL build does not emit `CONTROL HEADING FINAL` (the same block in `BOMRP010` never appears either); a generated detail always does | one report renderer with real grouping |
| `BOMRP030 MODE=COMPARE` accepts `COSTSET=` and prints it, but `BOMCOMP` values both revisions with the cost set hard-coded in `Cost-One-Revision` | an argument that is documented, printed and then ignored by the engine behind it | the comparison was costed years after the report learned the argument | push the cost set through `BOMCOMPCA` |
| `BOMCOMP` costs a revision comparison by costing the **parent item**, which re-selects the effective revision, so two revisions of the same parent can report the same cost | the cost impact is per item, not per revision | `BOMCOST` only takes an item and a date, never a bill identity | cost a named `BomHeaderId` |
| `BOMBULK` splits into `BOMBULK` (the run) and `BOMBREV` (one proposed revision) purely because one program would not fit the module's file-size rule | an arbitrary seam in the middle of one business transaction | the 2016 change request was capped at "no new LINKable programs", so the second half is a non-LINKable subprogram with its own parameter copybook | one service with internal classes |
| `BOMBREV` re-implements the header-and-line copy that `BOMJOB NEWREV` already does | the same `INSERT ... SELECT` pair written twice | `BOMJOB` owns its own `BEGN`/`COMT`, so calling it from inside `BOMBULK`'s transaction would commit half a bulk change | one revision-copy service that never opens a transaction of its own |
| `BOMBREV` finds the next free revision letter by probing `A` to `Z` with twenty-six single-row `SELECT`s | a loop of lookups instead of one `MAX` | that is what the 1996 program did, and it keeps the letters in the order engineering reads them | a sequence or a computed next revision |
| `BOMBREV` reuses `Look-For-That-Revision` both to ask "is this revision free?" and to read back the identity of the revision it has just inserted - the answer is left in `Ws-Col(1)` | one paragraph, two meanings, communicated through a shared buffer | saving a near-identical `SELECT` | a repository returning a typed result |
| `BOMBULK` asks `CYCLECHK EDGE` *and* `WHEREUSD ALL` to decide whether a replacement closes a loop | two engines asked the same question | `CYCLECHK EDGE` walks below the proposed child and so cannot see the proposed parent, which is the edge that matters for a bulk change | one reachability service that takes the proposed edge |
| `BOMBULK` writes the change set with autocommit and the bills inside `BEGN`/`COMT`, deliberately mixing the two | a preview that is rolled back still leaves its `bom.BomChangeLine` evidence behind | auditors asked for the preview to be recorded even when nothing was applied | an append-only audit stream separate from the business transaction |
| `QTYCHG` on the COMMAREA is `QTYCHANGE` in `bom.BomChangeLine.Action` and `bom.BomChange.ChangeType` | the same value spelled two ways, translated in `Translate-The-Action` | the screens have said `QTYCHG` since 1996 and the table was created in 2016 | one vocabulary |
| `BOMBULKCA` still accepts `COMMIT` and `RESULT` as function names alongside `APPLY` and `GETLINE` | two spellings of two functions | CR2442 named them `COMMIT`/`RESULT`; the rest of the module settled on `APPLY`/`GETLINE` | one set of verbs |
| `BOMBULK` changes only the **first** occurrence of a repeated component and reports the others in the detail text | a bulk change that is not quite bulk | BOM-002 keeps repeated lines distinguishable, and changing them all silently has lost an engineering department a day | an occurrence-level selection in the request |
| 132-column Report Writer output to `run\spool\*.lst` | line printer listings | that was the output device | HTML/PDF rendering from the same structured result |
| The spool name stamp `BOMRPnnn-<CO>-yyyymmddhhmmss.lst` is only second-accurate | two runs of the same report inside one second overwrite each other, which the indented and costed listings do when they are launched back to back from a script | the 1999 naming convention came from a nightly batch where two runs a second was impossible | a run id (`core.BatchRun`) in the file name |
| `BOMSUPCT` holds the eligible supply pool in a fixed table loaded once per netting run | netting works on a snapshot | consistent netting without long-held locks on the stock files | snapshot isolation or an explicit reservation service |
| Phantom handling duplicated: `BX-EXPAND-PHANTOM` in the engine *and* `SupplyBehaviour = 'PHANTOM'` on the component | a phantom can be declared on the item or on the occurrence | the item-level flag came first (1994), the occurrence-level override was added when a part was phantom in one bill only | one effective-phantom resolution, computed once |
| COBOL programs read the database through `SQLIO` cursors numbered 1-8 | cursor numbers are a shared, hand-managed resource | the SQL gateway supported eight concurrent statements | connection/statement objects with proper scoping |
| `docs` and the seed call the examples `DEMO-*` items | the spec's B1-B6 worked examples are seeded as real bills | demos must show the spec numbers | fixture data generated from the specification |
